## 4. Reviews

### 4.1 Independent design review (Codex gpt-6.1-sol, high effort, read-only, 12 October 2026)

Full text: lane `research/reviews/WP-01-design-review.md`. 12 findings: 2 P0, 10 P1. One review, no follow-up (LD-13).
The architect's disposition of each finding is an amendment to the design. The amendments bind the implementation;
where an amendment differs from `WP-01-design.md`, the amendment governs. A fix is checked by the architect against
the finding's scenario, not sent back to Codex.

| Finding | Rank | Disposition (amendment) | Unit |
|---|---|---|---|
| R-01 background refusals keep restricted content | P0 | **A-01.** Fix the class in `enhance.js`: every background request of a page (poll regions, any later fetch) treats 401, 403, 404, a redirect to a sign-in page, or a response without the expected region as an access change. The script stops every poller of the page at once, removes the region's restricted content, and navigates the page to its own address (`location.replace(location.href)`) so the server renders the authoritative state (SH-02 Denied or sign-in). It MUST NOT keep the old DOM. Tests: a gallery fixture whose poll answers 404, and one that redirects to sign-in, each assert the old content is gone and the page navigated. No product page polls in WP-01; the rule protects every later package (BU-P04 self-refresh, UAT-10). | U3 |
| R-02 back/forward cache keeps private pages | P0 | **A-02.** Every signed-in document and every sign-in, enrolment and status document carries `data-reload-on-restore` on `<html>`. On `pagehide` with `event.persisted` the script hides `main` (class on `<html>`); on `pageshow` with `event.persisted` it calls `location.replace(location.href)`, so the server authorizes again before anything shows. The sign-out answer carries `Clear-Site-Data: "cache"` so the browser drops cached private pages. Without JavaScript the residual (a browser that restores a no-store page) is recorded as a known limitation in the package record. Tests: browser test Back after sign-out shows the sign-in page, not the private page; Back after enrolment completion never shows the key. | U2 (attribute), U3 (script), U4 (sign-out header) |
| R-03 mixed-case address breaks the identical replay | P1 | **A-03.** The sign-in request handlers send the address trimmed and lower-cased (presentation normalization of the user's input; Core still validates it). An identical retry then has identical content and replays. The Core binding defect (normalization skipped on replay) goes to the orchestrator as proposal P-04. | U4 |
| R-04 receipt can claim acceptance it cannot check | P1 | **A-04.** The receipt title from `done` shows only when `core.operation` answers `accepted` and its `result.resource` kind matches the kind that `done` code expects (closed map). Otherwise the receipt reads "Request reference [key]. The receipt cannot be checked now." with no acceptance claim. A read failure never shows "accepted". | U3 |
| R-05 cookie lifetime not enforced by the server | P1 | **A-05.** The address cookie value is a versioned envelope: version byte, random 96-bit IV per seal, AES-256-GCM ciphertext of `{address, expiresAt}`, with the pre-session nonce as associated data. The key derives from the CSRF key with the label `tm-signin-address-v1`. The server refuses an envelope past `expiresAt` (15 minutes), with a bad tag, a wrong version or a size over a fixed bound. Tests: expiry, tamper, wrong nonce, oversize. | U4 |
| R-06 an old replay replaces the current address | P1 | **A-06.** The cookie is set only when the request command was newly executed (`outcome.replayed === false`). A replay keeps the current cookie. Test: request A, request B, replay A, the code step names B. | U4 |
| R-07 staff sign-in recovery across a TOTP rollover | P1 | **A-07.** An unresolved sign-in verification (TA or staff) never asks the user to repeat the same operation. The page says the sign-in result is unknown and offers "Request a new code" (a new request, a new challenge). No session token is ever delivered on a replay (existing Core rule), so starting again is safe. | U4 |
| R-08 a foreign operation key answers "no record yet" | P1 | **A-08.** Accepted as Core answers it: an unknown or another person's key reads "Nothing is recorded for request [reference] so far" (non-disclosure; the existing test stays). The acceptance items expecting 404 are corrected. | U5, PM |
| R-09 service state before and after session resolution | P1 | **A-09.** (a) The server's error boundary renders the category `maintenance` always through the status document, without shell, account or support-view details, even when a session was resolved earlier in the request. (b) A Core outage before the session read renders the uniform "TravelMudra is unavailable now" status page with "Do not send a request again until it is back" and no case data; the operation page's "Status unavailable" row covers only a failure of the operation read itself. | U4 (server boundary), U5 (copy) |
| R-10, R-11, R-12 acceptance items that test impossible or wrong behavior | P1 | **A-10 to A-12.** The Product Manager corrects the checklist rows named by the review only (A35, A37, A42, A49, A56, A65, A67, A70, A82, A83, A86, A89, A99, §1.2, V23), to match the architect's decisions of §3 and the actual contracts: identical replay versus changed-content conflict; mail failure tested at the worker boundary with the same neutral response; "we are sending a code"; combined code-failure text; no secret code preserved in a re-rendered field; receipt limitation; lag wording; email-change redirect separated from the generic session-ended page; enrolment uses revisions. | PM |
